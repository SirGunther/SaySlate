## Review Summary

Local Whisper is implemented as a second, explicit dictation provider next to the existing browser speech-recognition path (`WSI-01` through `WSI-06`). This review closes the integration with the least-privilege manifest permission, operator documentation, a completed cross-cutting secret/log review, and updated static verification (`WSI-07`) - including a single verification command (`node tests/verify.mjs`) that now runs every focused test itself rather than only checking that the files exist. All automated command-line checks pass. Live validation against a running WhisperService instance, a real microphone, and the installed extension remains pending and is not claimed as complete; the version bump to 1.12.0 is withheld until it passes.

### D1: Add Local Whisper Dictation Provider

Files: `manifest.json`, `whisperServiceClient.js`, `micCapture.js`, `micCaptureWorklet.js`, `pcmAudioProcessor.js`, `dictationSettings.js`, `dictationProviderPanel.js`, `background.js`, `offscreen.html`, `offscreenSpeech.js`, `app.js`, `floating.js`, `floatingSpeechClient.js`

#### Problem

- **Current Behavior(s):** SaySlate could only dictate through the browser's built-in speech recognition, with no option to use a private, locally hosted transcription service.
- **Expected Behavior(s):** SaySlate should offer Local Whisper as an explicit, user-selectable alternative, with its own visible availability state, while keeping Browser Dictation as the default for existing users.

#### Requirement(s)

- Add a compact provider selector using SaySlate's existing styling and interaction patterns, persist the selection and Local Whisper configuration through `chrome.storage.local`, and never switch providers automatically.

#### Solution(s)

- Added a dependency-light WhisperService protocol client (`whisperServiceClient.js`), a reusable microphone-to-PCM16 pipeline (`micCapture.js`, `micCaptureWorklet.js`, `pcmAudioProcessor.js`), a versioned settings module and toolbar panel (`dictationSettings.js`, `dictationProviderPanel.js`), a shared offscreen host (`background.js`, `offscreenSpeech.js`), and full-page/floating integration (`app.js`, `floating.js`, `floatingSpeechClient.js`).
- Browser Dictation remains the migration default (`dictationSettings.js`'s `normalizeRaw` falls back to `PROVIDERS.BROWSER` for any prior or missing settings).

#### Validation Details

- [x] `node tests/whisper-service-client.test.mjs`, `node tests/mic-capture.test.mjs`, `node tests/mic-capture-worklet.test.mjs`, `node tests/pcm-audio-processor.test.mjs`, `node tests/dictation-settings.test.mjs`, and `node tests/dictation-provider-panel.test.mjs` all pass.
- [x] `node tests/verify.mjs` confirms the provider toggle, settings panel, and script load order are wired into `app.html` and `floating.html`.

#### Requirement(s)

#### Solution(s)

- `chatGPTAdapter.js` was not modified; it has no awareness of which dictation provider produced the text it submits.

#### Validation Details

### D3: Isolate Each Dictation Run

Files: `background.js`, `offscreenSpeech.js`, `whisperServiceClient.js`

#### Problem

- **Current Behavior(s):** A shared offscreen host and a single WhisperService slot could, if implemented carelessly, leak partial or final text between unrelated dictation runs, or let overlapping start requests race.
- **Expected Behavior(s):** Every dictation run must get a fresh WhisperService session and microphone pipeline, with no session id, revision, or partial/final text ever carried into the next run, and overlapping starts rejected rather than double-connected.

#### Requirement(s)

- Create exactly one fresh service session and capture pipeline per run, reject a second concurrent start as busy, and reject events whose session id does not match the run they are routed to.

#### Solution(s)

- `background.js` serializes overlapping starts with an in-flight guard before a second HTTP session descriptor can ever be created.
- `offscreenSpeech.js` tracks one active Local Whisper session at a time, keyed by session id and origin, and normalizes/routes events only to the run that owns them.

#### Validation Details

- [x] `tests/background-routing.test.mjs` proves a second sequential start receives a brand-new session descriptor rather than reusing one, and that overlapping starts are rejected as busy before a second descriptor is created.
- [x] `tests/offscreen-speech.test.mjs` proves a second start while one run is active is rejected as busy, that stale/duplicate/late events are suppressed, and that a run's state is fully released before the next run starts.

### D4: Keep Credentials And Dictated Content Out Of Logs

Files: `background.js`, `offscreenSpeech.js`, `whisperServiceClient.js`, `dictationSettings.js`, `dictationProviderPanel.js`

#### Problem

- **Current Behavior(s):** Introducing a bearer token and a streamed transcript creates a new opportunity to leak either into source, logs, URLs, or extension messages.
- **Expected Behavior(s):** The bearer token must never be exposed by the settings UI, never included in a relayed extension message, never appear in a WebSocket URL, error text, or console output, and the offscreen document - which owns the microphone and the streaming WebSocket - must never read it at all; dictated audio/transcript text must never be logged as a diagnostic.

#### Solution(s)

- `dictationSettings.js` persists the token under `bearerToken` in `chrome.storage.local` and reads that same record back when loading settings in the full-page and Floating Slate contexts, but exposes only `hasToken: Boolean(raw.bearerToken)` to the UI; the token `<input>` is cleared immediately after every save, open, and close, so the raw token never leaves that module.
- `background.js` is the only file that constructs a `SaySlateWhisperClient` (the only place the token is actually used to make an authenticated request); every message it relays to the offscreen document carries a session descriptor, never the token.
- `offscreenSpeech.js` - which owns the microphone and the streaming WebSocket - contains no reference to `chrome.storage` or `bearerToken` anywhere in the file, so it never reads or holds the token at all.
- `whisperServiceClient.js` builds the WebSocket URL from only `descriptor.streamUrl` and a `ticket` query parameter, and redacts the token out of any HTTP error message before it is thrown.
- A source-level review found two pre-existing `console.warn` calls in the extension (`background.js`, `floatingHost.js`), both for unrelated shortcut-routing failures with no token, audio, or transcript content; no new logging was added by this work.

#### Validation Details

- [x] `node tests/verify.mjs` statically confirms the offscreen document never references `bearerToken`/`chrome.storage`, that background.js is the only place a `SaySlateWhisperClient` is constructed, and that the WebSocket URL construction never embeds the token.
- [x] `tests/whisper-service-client.test.mjs` proves the bearer token appears only in HTTP authorization headers and never in a WebSocket URL or a returned diagnostic.
- [ ] Confirm live that no token, transcript, or audio content appears in the browser's extension console during an actual dictation run.

### D5: Grant Least-Privilege Manifest Access

Files: `manifest.json`, `tests/verify.mjs`

#### Problem

- **Current Behavior(s):** The manifest granted host access only to the Google Generative Language API; it had no permission to reach the local WhisperService origin at all.
- **Expected Behavior(s):** The manifest should grant exactly the fixed WhisperService loopback origin needed for this feature, and nothing broader.

#### Requirement(s)

- Add only `http://127.0.0.1:8178/*`; no wildcard, LAN, or public HTTP host may be introduced.

#### Solution(s)

- Added `http://127.0.0.1:8178/*` to `host_permissions` alongside the existing Google Generative Language host.
- Added a static allow-list assertion in `tests/verify.mjs` that fails if `host_permissions` ever contains anything other than these two exact entries.

#### Validation Details

- [x] `node tests/verify.mjs` confirms `manifest.json` parses and grants only the two expected host permissions.
